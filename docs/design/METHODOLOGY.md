# 方法论 — 如何与 AI Agent 协作编程

> 本文档是 ThinCoder 三观的实践延伸：三观回答"为什么"，方法论回答"怎么做"。
> 面向所有使用 AI Agent 做项目的人——不限于 ThinCoder，也适用于其他 Agent 工具。

---

## 0. 一句话速查

**总览**：你说需求 → Agent 探索/规划/实施 → 你看 diff 和测试 → 过，或者纠错。

| 你想做的事 | 对 Agent 怎么说 |
|---|---|
| 了解陌生项目 | "帮我梳理一下这个项目的架构" |
| 加小功能 / 修 bug | 一句话描述需求，等它做完看 `git diff` |
| 改架构 / 重构 | 描述需求 → 等它出 plan → 审批 → 说"开始做" |
| Agent 改错了 | "上一轮改错了 X，原因可能是 Y，请重新做" |
| Agent 方向偏了 | "方向不对，应该先做 A 再做 B" |
| 不确定需求细节 | 说"先出个方案我看看"，别让它猜着做 |
| 反复改不好 | 停下来，换个说法重新描述需求 |
| 跨会话继续 | 关键决策用 `memory_put` 存，新会话用 `memory_search` 找回 |
| 验证工作 | 看 `git diff` → 看关键路径代码 → 看测试覆盖 |

## 1. 项目启动

### 1.1 写好 README 和设计文档

Agent 通过 `doc_search` 检索项目文档来理解意图。你写下的文字，就是 Agent 的"项目记忆"。

**README 放什么：**
- 项目是什么、解决什么问题
- 技术栈选型
- 怎么跑起来（一条命令最好）
- 目录结构概览

**设计文档放什么：**
- 核心架构决策及理由（为什么选 A 不选 B）
- 模块之间的接口约定
- 数据库/协议 schema
- 已知的技术债和计划中的重构

**`AGENTS.md` 放什么：**
- 项目特有的硬约束（比如技术栈限制、必须兼容的环境、不能引入的依赖类型）
- 命名约定、代码风格
- 提交信息和发版流程

> 一句话的需求也能启动，但信息越充分，Agent 的产出越准。不确定哪个细节重不重要——写上，Agent 会用到的。

### 1.2 准备上下文

开始一个新任务前，确保 Agent 能看到：
- 当前 git 状态（branch、recent commits）——系统自动注入
- 工作目录快照——系统自动注入
- 相关代码的索引——系统自动注入

不需要手动准备。但如果某些背景知识不在代码里（比如业务逻辑、第三方 API 的限制），写在第一条消息里。

## 2. 协作节奏

### 2.1 三种任务规模

| 规模 | 描述 | 协作方式 |
|---|---|---|
| **小** | 修 bug、改文案、加个参数 | 一句话 → Agent 做 → 看 diff → 过 |
| **中** | 加功能、重构模块 | 描述需求 → Agent 进 plan mode 出方案 → 审批 → 实现 → verify |
| **大** | 新模块、架构变更 | 拆成多个中任务，逐个推进。关键决策用 `memory_put` 跨会话传递 |

### 2.2 一个会话做一件事

不要在一个会话里攒一堆需求。上下文越长，Agent 越容易跑偏。做完一件事、确认无误后，开新会话做下一件。

判断标准：你开始觉得 Agent "忘了前面说的"或者"一直在重复"——就该开新会话了。

### 2.3 跨会话传递关键信息

以下情况用 `memory_put` 保存到 Agent 记忆：
- 做了一个架构决策（为什么选这个方案）
- 发现了一个难以排查的 bug 的根因
- 约定了一个之后要遵守的项目规范

之后任何会话里，Agent 都能通过 `memory_search` 找回这些信息。不需要你每次重新解释。

## 3. 评审策略

### 3.1 看什么

**看架构决策 > 边界条件 > 代码风格**

Agent 改了一个函数签名，把调用点都修了——这是 Agent 该做的，不需要你逐行审。你该看的是：这个设计方向对不对？会不会引入新的耦合？边界条件覆盖了吗？

> 代码风格是 Agent 的强项——格式、命名、模式识别。把精力留给更重要的事。

### 3.2 怎么看

- **`git diff`** 先看改动范围——文件数量、增删行数、改动的模块。范围异常大或异常小都值得追问。
- **关键路径读原文**——只读你关心的函数或模块，不是全部文件。
- **看测试**——Agent 加没加测试？测试覆盖了什么场景？

### 3.3 什么时候介入

- Agent 问你问题——回答。它在请求你的判断，不是在绕路。
- 你已经看出方向不对——直接说。别等它跑偏了三轮再纠正。
- Agent 没问但你有个更好的主意——说出来。Agent 的 plan 不是圣旨，是你的草稿。

## 4. 信任边界

### 4.1 可信任的

- **语法和格式**：不会写错
- **常规模式**：CRUD、配置加载、错误处理——这些是肌肉记忆
- **工具使用**：知道什么时候用 `read`、什么时候用 `grep`

### 4.2 需要验证的

- **业务逻辑**：需求描述 → 代码实现之间的映射是否正确——跑测试验证
- **算法正确性**：复杂计算、状态机——跑测试验证
- **边界条件**：空值、超时、并发——让 Agent 自己描述它考虑了哪些，你判断够不够

### 4.3 需要你评审的

- **架构决策**：拆不拆新模块、用哪个设计模式——Agent 出选项，你拍板
- **新增依赖**：引入第三方库——Agent 应该先问你能不能
- **安全相关**：鉴权、加密、用户输入处理

## 5. 纠错

### 5.1 Agent 改坏了

- **能 undo 的**：用 git 撤销改动的文件，回到上一个版本。
- **不能 undo 的**：告诉 Agent "你上一轮改错了 X，原因可能是 Y，请重新做"。给原因比给指令更有效。

### 5.2 方向偏了

直接说。不用委婉——Agent 不会受伤。"你这个方向不对，应该先做 A 再做 B" 比 "嗯…你能不能再想想" 高效得多。

Agent 偏了通常是因为：
- 需求没说清楚 → 重新组织语言，补充约束条件
- 它自己在猜 → 告诉它"别猜，不确定就问我"
- 上下文太长杂了 → 开新会话，只给关键信息

### 5.3 反复改不好

这通常不是 Agent 能力问题，是**需求本身有问题**——太模糊、自相矛盾、或者在错误的方向上优化。停下来，重新想一遍"我到底要什么"，然后重新描述。换一种说法往往比多改三轮更有效。

### 5.4 诊断表：Agent 做错了，根因在哪

| 现象 | 常见根因 | 怎么修 |
|---|---|---|
| 实现的和你想的不一样 | 需求没说清楚，Agent 在猜 | 加约束条件重新描述 |
| 反复改、总是差一点 | 需求自相矛盾，或者方向错了 | 停下来，重新想"我到底要什么"，换一种说法 |
| Agent 一直在重复、不推进 | 上下文太长太杂，迷失了 | 开新会话，只给关键信息 |
| 改了不该改的文件 | 没说清楚范围 | 告诉它"只改 X 文件，别碰 Y" |
| 产出看起来对但跑不通 | 缺环境信息或业务规则 | 在第一条消息里补充背景 |
| Agent 自己跑偏了 | 它在猜你的意图 | 告诉它"别猜，不确定就问我" |
| 测试失败但 Agent 说完成了 | 验证步骤被跳过 | 让它跑完整测试套件再交差 |

## 6. 常用模式

### 6.1 探索 → 规划 → 实施

```
"帮我看看这个项目的认证模块是怎么设计的"
→ Agent 用 explore 子 agent 并行搜索
→ 出分析报告

"好的，现在帮我加一个 token 刷新机制"
→ Agent 进 plan mode
→ 出方案（改哪些文件、怎么改）
→ 你审批

"开始做"
→ Agent 实现 → verify → 完成
```

### 6.2 小步快跑

不要一次给 Agent 丢 10 个需求。从最小的可验证改动开始：

```
第一轮："把 login 函数拆成两个：validate 和 authenticate"
→ 改完 → verify → 确认

第二轮："给 authenticate 加上 token 过期检查"
→ 改完 → verify → 确认
```

每轮改动的 blast radius 小，出问题容易定位。

### 6.3 让 Agent 自己审自己

改完之后，Agent 会跑 verify——你应该看它的 verify 报告。如果报告里有 `✗ Tests FAILED`，Agent 还没完成，它会自己继续修。

但如果 Agent 说"完成了"而你发现遗漏了——直接指出，别替它修。修是 Agent 的事，审是你的事。

### 6.4 完成检查清单

Agent 说"完成"后，过一遍：

- [ ] **看 diff 范围**：改的文件对不对、有没有不该动的
- [ ] **看关键代码**：关注你关心的函数或模块，不用逐行
- [ ] **看测试覆盖**：Agent 加了测试吗？覆盖了边界条件吗
- [ ] **看验证结果**：`npm test` 绿了吗（不是 Agent 说"应该能跑了"）
- [ ] **看交代**：Agent 有没有说清楚改了什么、为什么改、有没有风险
- [ ] **确认收工**：没问题就过；有问题直接指出，别替它修

## 与三观的对应关系

| 三观 | 方法论 |
|---|---|
| 世界观：人是决策者，Agent 是代码负责者 | §3 评审策略 — 人看方向，Agent 管实现 |
| 世界观：充分沟通优先 | §1.1 写好文档 — 信息充分，Agent 才充分 |
| 世界观：模型理解力不是瓶颈，信息才是 | §1.2 准备上下文 — 给够信息，别让 Agent 猜 |
| 世界观：设计文档是 spec | §1.1 写好文档 — 设计文档定义了意图，读它比猜它便宜 |
| 人生观：勇于提出建议 | §3.3 什么时候介入 — Agent 的建议是草稿，你有否决权 |
| 人生观：做完要交代 | §6.2 小步快跑 — 每轮 verify，可验证的完成 |
| 价值观：关联问题不回避 | §3.1 看 diff 范围 — 改动范围异常要追问 |
| 价值观：诚实 > 体面 | §5 纠错 — 直接说，别绕弯 |
